ANALYSTGPT BENCHMARK: CREDIT CARD FRAUD DETECTION

OBJECTIVE

Perform a complete, reproducible machine-learning investigation to detect fraudulent credit card transactions using the uploaded creditcard.csv dataset.

This is a supervised binary classification task. The target column is Class, where 1 represents fraud and 0 represents a legitimate transaction.

The primary objective is to identify fraudulent transactions while carefully evaluating false positives, false negatives, class imbalance, data leakage, and generalization to unseen transactions.

Do not modify the system configuration or invent results to satisfy this request. Execute the planned workflow using the available agents and tools.

1. PLANNING AND TASK SELECTION

The Planner Agent must produce an execution plan before downstream execution.

The plan must cover dataset inspection and data-quality validation, exploratory data analysis and class-imbalance analysis, data preprocessing and feature engineering where justified, leakage-safe train/validation/test separation, baseline establishment and model training, model comparison and validation-based model selection, validation-only decision-threshold selection, final evaluation on held-out test data, artifact verification, and evidence-based reporting.

Assign tasks to the appropriate agents. The DataAnalystAgent must handle data inspection, cleaning, exploratory analysis, and justified feature engineering. The ML Agent must handle model training, model comparison, tuning, and evaluation. The Reporter Agent must synthesize the actual verified outputs.

Do not add unnecessary tasks or train models without a clear evaluation purpose.

2. DATASET INSPECTION AND DATA QUALITY

Inspect the original dataset before modifying it.

Record the original row and column counts, column names and data types, target distribution, class proportions and imbalance ratio, missing values, duplicate rows, invalid values, summary statistics for Time, Amount, and relevant numeric features, and potential data leakage or suspiciously target-related features.

Investigate duplicate records and anomalies before deciding whether any should be removed. Preserve the original data and document all transformations, exclusions, and resulting row counts.

Do not assume that every unusual value is erroneous. Do not fabricate missing values or silently delete observations.

3. EXPLORATORY DATA ANALYSIS

Produce useful, readable visualizations that explain fraud versus legitimate transaction counts and percentages, transaction amount distributions including an appropriate treatment of skew, fraud patterns across transaction time where supported by the data, relationships between selected features and the target, and relevant data-quality findings.

Handle the severe class imbalance when choosing visualizations and interpreting results. Do not claim causal relationships from correlations.

Save the plots and a structured summary of the main findings.

4. DATA LEAKAGE PREVENTION AND SPLITTING

Use Class exclusively as the prediction target.

Inspect the meaning and ordering of Time before selecting a splitting strategy. Evaluate whether a chronological split is appropriate for this dataset. Prefer a chronological train/validation/test split when the data's ordering supports it. Otherwise, justify an alternative and document its limitations.

If using a chronological split, use the earliest 60% of observations for training, the next 20% for validation, and reserve the latest 20% as the final test set.

Verify class counts in all partitions before training. If the split creates an unusable partition, explain the issue and select a defensible alternative without examining test labels to tune the model.

Fit imputers, scalers, feature selectors, dimensionality reduction, and other learned preprocessing steps using training data only. Apply fitted transformations to validation and test data without refitting.

Never use test data for model selection, hyperparameter tuning, oversampling, feature selection, or threshold selection. If using resampling, apply it only to training data and only within the relevant training folds.

Do not use Class or any target-derived information as an input feature.

5. FEATURE ENGINEERING

Assess whether existing features are sufficient before adding new ones.

Consider justified transformations such as a log transformation of Amount, provided they are implemented without leakage and evaluated appropriately.

Do not automatically apply PCA to V1 through V28. These features are already anonymized PCA-transformed variables. Preserve the original features unless an experiment provides a defensible reason to change them.

Record the final feature list, transformations, and rationale.

6. MODEL TRAINING AND COMPARISON

Establish a simple baseline, such as a majority-class DummyClassifier, to demonstrate why accuracy alone is insufficient.

Train and compare appropriate classification models supported by the environment. Prefer a manageable set, such as Logistic Regression with appropriate scaling and class-imbalance handling, Random Forest, and a gradient-boosting classifier available in the installed environment.

Do not install expensive services or require paid APIs. Do not assume a library is installed without checking.

Use suitable class weights or other imbalance-handling techniques where justified. Tune hyperparameters using training/validation data or cross-validation confined to the training partition.

Use a fixed random seed wherever applicable. Record model configurations and failures honestly. Do not force a particular model to win.

7. EVALUATION METRICS AND THRESHOLD SELECTION

Report the following for the baseline and each viable candidate:

Precision, recall, F1-score, PR-AUC or average precision, ROC-AUC, balanced accuracy, confusion matrix, false positives, false negatives, fraud-class support, and the threshold used for classification.

Explain why accuracy is insufficient for this highly imbalanced task. Include precision-recall analysis and discuss the trade-off between catching fraud and incorrectly flagging legitimate transactions.

Select the decision threshold using validation data only. Explain the selection criterion, such as maximizing validation F1 or meeting a justified minimum precision or recall requirement.

Do not choose the threshold based on the final test results.

After model selection and threshold selection are complete, evaluate the selected model once on the untouched test set. Report the default-threshold and selected-threshold results separately where meaningful.

If a metric is undefined or cannot be computed reliably, state that explicitly instead of inventing a value.

Do not generate empty, placeholder, or fabricated artifacts. If an artifact cannot be produced, record the reason.

9. INDEPENDENT VERIFICATION

Before reporting success, verify the artifacts against the actual execution outputs.

Check that dataset row counts reconcile across all documented transformations; train, validation, and test indices do not overlap; preprocessing was fitted only on training data; the target is absent from model input features; no resampling was performed on validation or test data; the selected model and threshold were determined without using test results; test metrics recomputed from saved predictions match the reported metrics within reasonable numerical tolerance; confusion-matrix counts agree with the test labels and predictions; reported feature names match the serialized pipeline or model inputs; and every artifact claimed in the final report actually exists and contains valid data.

Separate confirmed defects from warnings, unverified claims, and checker limitations. Do not classify a warning as a demonstrated analytical failure without evidence.

If a verification check fails, identify the exact discrepancy and its impact. Attempt only bounded, targeted repairs where appropriate. Do not repeatedly rerun the entire workflow without a justified reason.

10. FINAL REPORT

Produce an evidence-based report covering dataset characteristics and quality, class imbalance and its implications, cleaning and feature-engineering decisions, splitting strategy and leakage safeguards, baseline and model-comparison results, validation-based threshold selection, final held-out test performance, false-positive and false-negative implications, important limitations and potential deployment risks, and reproducibility instructions and artifact locations.

Distinguish validation results from final test results. Do not claim that a model is production-ready solely because it performs well on this dataset.

ACCEPTANCE CRITERIA

Consider the workflow successful only if it completes the planned analytical tasks, prevents target leakage and test-set contamination, uses appropriate metrics for severe class imbalance, selects the model and decision threshold without optimizing on test data, generates substantive artifacts that agree with the reported results, independently verifies test metrics from saved predictions, and produces a final report grounded in the actual artifacts.

Prioritize analytical correctness, reproducibility, and honest verification over the number of models, charts, tool calls, or files generated.

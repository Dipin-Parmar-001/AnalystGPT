# Unified Observability: Local JSONL Mirroring + Latency/Token Metrics + Standalone Dashboard

Logfire stays exactly as-is. Everything below is additive.

## 1. New core module: `agents/observability.py`

A process-wide `RunRecorder` singleton owning per-run state:

**JSONL logging** — `start_run()` creates `logs/run_<YYYYmmdd_HHMMSS>_<pid>.jsonl` (one unified file per run; everything goes in it). `log_event(event, level, **attrs)` appends one thread-safe, flushed JSON line: `{ts, event, level, run_id, ...attrs}`. `finalize(status)` writes a final `run_summary` event (all counters) into the JSONL plus `run_metrics.json` into the run output dir for durability.

**Smart chunking (your 15000-token rule)** — `smart_chunk_text(text, token_limit=15000)` reuses tiktoken via `count_tokens` from `memory_manager.py`. Texts over 15000 tokens are cut from the MIDDLE: head + tail kept (~40% each) with marker `... [middle truncated: N tokens -> first X + last Y] ...`. Applied to every string value in logged attrs (code, stdout, stderr, prompts, tracebacks), so no log line is unbounded.

**Logfire mirroring (zero changes to the 149 existing call sites)** — `patch_logfire()` wraps `logfire.info/warn/error/debug/trace` so each call goes to Logfire unchanged AND mirrors message + all attributes to the JSONL. `logfire.span(...)` is wrapped to emit `span_start`/`span_end` (duration, exception) events. Patched once inside `setup_logfire()` in `agents/logger.py` — since all modules resolve `logfire.info` at runtime, everything currently sent to Logfire lands in the local file too.

**LLM call instrumentation** — `instrument_openai_client(client, agent_name)` wraps `client.chat.completions.create` and records one `llm_call` event per call (see §3 for what's captured). Also attaches a best-effort httpx response-header hook to grab Portkey metadata (`x-portkey-provider`, `x-portkey-retry-attempt-count`, `x-portkey-cache-status`); guarded with try/except so it can never break a call.

**Metrics API** — `timer(name)`, `increment(key)`, `add_duration(key, s)`, duration lists for percentile math, named `step_start/step_end` for the workflow timeline, `snapshot()`; plus a `ContextVar`-based task context (`set_task_context(task_id, agent, phase)`) set by the orchestrator so every LLM/tool event is attributed to the right agent AND task.

## 3. Metrics captured (your list, exactly)

All latency metrics keep the full duration list and are reported as **avg, min, max, p50, p90, p95, p99** — overall, per agent, and per task.

1. **LLM call latency per agent and per task** — each `llm_call` event: `duration_s` (wall time we measure), `agent`, `task_id`, `phase`, plus attribution rolled up per agent and per task. Planner/judge calls attributed to `planning`/`verification` phases.
2. **Tool call latency** — `tool_executed` events with `duration_s` from the sandbox result; percentiles overall, per tool, per agent, per task.
3. **Token usage — three groups**, per agent and per task:
   - **Total tokens (no caching logic)**: API-reported `usage.prompt_tokens` / `completion_tokens` / `total_tokens` (includes re-sent history).
   - **Cachable tokens (new-only)**: per call we token-count the outgoing message list (tiktoken, via `count_message_tokens`) and subtract the previous call's count for the same agent+task — i.e. only the tokens that are genuinely NEW this call, excluding the previously-shared message history re-sent along with the prompt. Baseline resets on context compaction (when the count shrinks) and on task change.
   - **Provider-cached tokens (bonus)**: `usage.prompt_tokens_details.cached_tokens` when the provider reports it (your example JSON shows this field from Portkey/OpenRouter).
4. **Success/failure with rates** — `llm_calls_total/success/failed` + failure % (overall and per agent/task), `tool_calls_total/success/failed` + failure % (overall and per tool). Retry events counted separately (agent-level LLM retries, validation retries, Portkey retry-attempt-count header when available).
5. **Real model name from the Portkey response body** — per call we record `served_model` from the response object (`resp.model`, e.g. `"inclusionai/ling-3.0-flash-fin:free"` in your example), `provider` from the response body (`resp.provider`, e.g. `"openrouter"`), the Portkey headers when capturable, AND `requested_model` (what was asked for). The hardcoded nemotron name only appears as `requested_model`; the dashboard aggregates latency/tokens **by served model**. No fabricated names.

## 4. Dashboard API: new `backend/api/observability.py`

- `GET /api/observability/runs` — list run JSONL files (id, size, modified, status).
- `GET /api/observability/runs/{run_id}` — aggregated view reduced from the JSONL: KPIs, percentile tables, step timeline, per-task, per-agent, per-tool, per-model, LLM calls, errors.
- `GET /api/observability/runs/{run_id}/events` — paginated events with level/event/text filters + `after` cursor for live tailing.
- `backend/app/main.py`: include router + serve dashboard at `/observability`.

## 5. Standalone dashboard: new `observability_dashboard/`

Plain HTML/JS/CSS, no build step, fully separate from the React frontend — served at `http://localhost:8000/observability`:

- Run selector + 2s live auto-refresh for the active run.
- KPI cards: total workflow latency, plan creation time, LLM total latency + call count + failure rate, tool total time + success rate, retry count, tasks completed/failed/skipped, artifacts, warning/error counts.
- Percentile latency tables (avg/p50/p90/p95/p99) for LLM calls (per agent + per task) and tool calls (per tool).
- Token usage tables per agent/task: total, cachable (new-only), provider-cached.
- Per-model breakdown table (served model, provider, calls, latency, tokens).
- Workflow Gantt timeline: planning → tasks → synthesis → verification → repair.
- Tool-call table with expandable full code/stdout/stderr (middle-truncation markers visible).
- Filterable event log viewer (level, event type, text search).
- Pure CSS bar charts — zero external dependencies.
